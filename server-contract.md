# Brigade API v1

The UI displays only product content. This document is for implementation and verification.

ES module entry: `handleApi(request, env, ctx, {sendPush} = {})` from `worker/api/index.mjs`. Returns `Response` for `/api/v1` and descendants; returns `null` for other paths. Root Worker serves static assets separately. Storage interface: `DB` and `BUCKET`. Production uses Supabase PostgreSQL/private Storage through server-only adapters; D1/R2 remain supported for local testing/fallback. The Supabase Edge entry rewrites `/functions/v1/brigade-api/<route>` into `/api/v1/<route>`; frontend base is `https://ufwrdwndlzwxtlkougrv.supabase.co/functions/v1/brigade-api`. Deploy with gateway JWT verification disabled, because the app checks its own opaque bearer sessions. SUPABASE_SERVICE_ROLE_KEY is an automatic Edge secret, never passed to the browser. Root owns push encryption/delivery.

All responses have `Cache-Control: no-store`. All shared reads/writes require `Authorization: Bearer <token>`. Health, registration and login are the only unauthenticated routes. Same-origin HTTPS clients may also use the optional HttpOnly/Secure/SameSite=Strict cookie. Cross-origin app clients use bearer tokens. Allowed origins: same origin, `https://colin-ru.github.io`, `https://appassets.androidplatform.net`, HTTP(S) loopback development. Others return 403. CORS is exact-origin, never `*`.

Success JSON is described below. Errors: `{error:{code,message,details?}}`, HTTP 400/401/403/404/409/413/415/429/500/503. No SQL errors or credential data reach the client. 429 includes Retry-After. Dates are ISO UTC. IDs are opaque strings. Text is plain text and must be rendered with textContent. Job position is descriptive and grants no administrative rights.

## Identity and profiles

- `GET /api/v1/health` → `{ok:true}` (no data or diagnostics).
- `POST /auth/register` body `{login,password,nickname,position,grade?,remember?}` → `{user,token,expiresAt}`. Login is lowercase, 3–40 ASCII letters/digits/`._-` and begins with a letter/digit. Nickname 2–60 characters. Password 4–128 characters, maximum 512 UTF-8 bytes; the same bounds apply to login. Position `operator|master`; grade `3|4|5|6|null`.
- `POST /auth/login` body `{login,password,remember?}` → same envelope. `remember` defaults true; true expires in 30 days, false in 24 hours. Password must never be saved by the client. Store bearer in localStorage for remember=true or sessionStorage for false.
- `POST /auth/logout` → `{ok:true}`; atomically revokes this session and removes native FCM bindings associated with this session. Other sessions/devices remain intact.
- `GET /me`, `PATCH /me` → `{user}`. Patch permits `{nickname?,position?,grade?,avatarMediaId?:id|null}`; avatar must belong to the caller.
- `GET /profiles?after=<profile-id>&limit=100` → `{items:[user],nextCursor:null|string}` (authenticated only; max100).

`user = {id,login,nickname,position,grade,avatarMediaId,createdAt,updatedAt}`. Passwords use PBKDF2-SHA256, 100000 iterations, random 128-bit salt and 256-bit derived hash, with parameters embedded in the stored string. This is the hosted Workers PBKDF2 ceiling; verification never lowers it. Sessions use random 256-bit tokens; DB stores SHA-256 only, expiry/revocation; at most ten sessions per user. Registration: 30/hour/IP to allow a brigade on shared Wi-Fi/CGNAT. Login: 20/15min/IP and 10/15min/login, including failed attempts. All authenticated writes: 120/min/user. Rate keys are hashed and expired rows are pruned in bounded batches.

## Media

- `POST /media`: multipart/form-data, exactly one `file`, optional `clientId` (same rules as messages). JPEG/PNG/WebP, <=2097152 bytes, declared MIME must match magic bytes. → HTTP201 `{media:{id,mimeType,size,createdAt}}`; same clientId and content retry → HTTP200 same media with `duplicate:true`; changed content409. Upload limit20/hour/user. R2 keys and original filenames are not exposed.
- `GET /media/:id`: authenticated image body, no cache. Use authenticated fetch → Blob URL in the UI; no bearer in query strings.
- `DELETE /media/:id`: authenticated owner only, removes unreferenced media metadata and the private storage object → `{ok:true}`. Another owner403; missing404; any live chat/note attachment or profile avatar reference409 `media_in_use`. Detach/delete the referencing records first. Storage failure restores metadata so the owner can retry. No public storage URL or service credential is exposed.

All brigade users may view shared images after authentication. Only their uploader can attach media to a new message/note/avatar. Up to three distinct media IDs per message. The frontend resizes phone images before upload. No image processing credentials or public bucket are needed.

## Chat and object notes

- `GET /chat/messages?before=<cursor>|after=<cursor>&limit=50` → `{items,nextCursor}`.
- `POST /chat/messages` body `{clientId,body?,mediaIds?:[]}` → HTTP201 `{item,duplicate:false}`; exact retry → HTTP200 `{item,duplicate:true}`. A reused clientId with changed content returns409. clientId 8–80 ASCII letters/digits/`_-` (UUID works). body <=4000 characters, text or media required.
- `PATCH /chat/messages/:id` body `{body?,mediaIds?,revision?}` → `{item}`; `DELETE` → `{ok:true}`; owner only.
- `GET /objects/:encodedKey/notes`: same paging envelope.
- `GET /notes/:id` → `{item}` for direct links to older notes/replies, authenticated. `GET /chat/messages/:id` is also supported.
- `POST /objects/:encodedKey/notes`: same creation body plus `parentId?:noteId|null`. Parent must belong to the same object. Reply creates one persisted notification for parent author, excluding self-replies.
- `PATCH /notes/:id` body `{body?,mediaIds?,revision?}` → `{item}`. `DELETE /notes/:id` → `{ok:true}`. Owner only, independent of position. If revision is supplied, stale edits return409.

`item = {id,cursor,clientId,body,author,media:[],createdAt,updatedAt,revision,objectKey?,parentId?}`. `author = {id,login,nickname,position,grade,avatarMediaId}`. `media[]` entries use the media envelope fields above. Items are always oldest→newest within each page. Default page is latest50. `before` selects older records; `after` selects newer. `nextCursor` is the appropriate boundary only if another page exists. Each item.cursor is usable for polling newer messages with after.

Object keys, URI encoded as one path segment: `pad:<pad>`, `well:<pad>:<wellId>`, `equipment:<pad>:<kind>`. Pad/well combinations must exist in the imported registry. Equipment kinds: `agzu`, `btma`, `bg`, `drainage`, `control-stations`, `cable-racks`. Accepting an equipment key does not assert it physically exists. Default object status is unknown; no equipment/status data are fabricated.

For pads with multiple confirmed positions, equipment keys are `equipment:<pad>:p1:<kind>` and `equipment:<pad>:p2:<kind>`; only positions in the generated registry are accepted. Legacy three-part keys on such a pad canonicalize to p1. On a single-position pad, p1 canonicalizes to the legacy three-part key. Notes, media attachments, statuses and notifications preserve the canonical position key; a reply parent from another position is rejected.

## Samples, statuses and shifts

- `GET /samples?padId=<optional-pad>` → `{period,items:[sampleItem]}`. Returns27 participating pads when omitted. Pads165Б,512,165,291,516 are excluded from sampling via source registry metadata; explicit GET for one of these returns `{period,items:[]}`, including when historical database rows exist.
- `period = {key:'YYYY-MM:rN',month:'YYYY-MM',round:1|2|3|4,startDate,endDate,isBreak,timeZone:'Asia/Yekaterinburg',startsAt,endsAt,nextStartDate,nextStartsAt,asOf}`. UTC+05 rounds are1–7,8–15,16–23,24–min(30,last day). startsAt is inclusive and endsAt exclusive. On31, period.key remains round4, isBreak=true, and previous round4 results remain visible read-only. February round4 ends28/29. Metadata comes from the database clock; the phone's timezone does not define a round.
- `sampleItem = {padId,periodKey,selectedWellIds:string[],productionWellIds:string[],totalWells,sampledCount,progress:'none'|'partial'|'done',sampled,revision,updatedAt,author,note}`. Production IDs are deduplicated exact source well.id values with type production, including any letters. totalWells counts these production IDs; selectedWellIds is their selected subset in source order. sampled is true only when totalWells>0 and every production well is selected. Zero production means no inferred inventory: empty arrays, counts0, none, sampled=false. A new round projects an empty selection/note/null author/time while retaining the stored monotonic revision; no rows or audit entries are deleted.
- `PUT /samples/:pad` body `{periodKey,wellIds:string[],revision:number,note?:string}` → `{item,period}` replaces the selected set. Validate exact IDs from this pad's production list; duplicates normalize to a set, invalid/non-production/foreign-pad IDs return400. Up to100 supplied entries; note<=1000. Alternatively `{periodKey,sampled:boolean,revision,note?}` selects all production wells or none. wellIds and sampled must not be combined; one is required. periodKey is mandatory: missing400 sampling_period_required; different current period409 sampling_period_changed;31st409 sampling_break. Both period409 responses include the complete error.details.period. Optimistic revision is mandatory; first revision0. On stale revision409 includes the complete error.details.current sampleItem. The SQL mutation also checks the actual database time window, preventing a request validated before midnight from writing into a new circle. Each successful update atomically stores the JSON selection, round_key and a new audit row.
- Nullable samples.well_ids and sample_audit.well_ids retain all previous NULL rows unchanged. NULL+sampled=true projects to all current production IDs; NULL+false projects to none. Reads never rewrite this historical data. Every explicit new update, including a legacy boolean request, stores a canonical JSON array; older audit rows remain NULL.
- Nullable round_key is written only on new explicit updates. Historical NULL round keys derive their period from the saved updated_at/created_at timestamp; no historical row is backfilled. Full audit/history remains stored across all circle/month/year changes.
- PUT for an excluded pad returns400 `sampling_excluded` with a clear message. Historical marks and audit remain untouched; this exclusion changes neither the32-pad map/well registry nor well types.
- `GET /objects/:encodedKey/status` → `{status,revision,updatedAt,author,note}`. Missing state: unknown/revision0/null author and time.
- `PUT /objects/:encodedKey/status` body `{status:'unknown'|'ok'|'attention'|'stopped'|'absent',revision,note?}` → status envelope. `absent` («Отсутствует») is available only for equipment keys; pad/well attempts return400 `equipment_status_only`. Equipment positions retain independent statuses. Any equipment can later change from absent back to ok using the normal revision/audit rules. The database CHECK also restricts absent to equipment; previous statuses, notes, images and audit remain intact.
- `GET /shifts?from=YYYY-MM-DD&to=YYYY-MM-DD` → `{items,nextCursor:null}`, max93-day range and1000 results. `POST /shifts` body `{date,kind:'day'|'night',note?,startAt?,endAt?}` → `{item}` (one record per user/date/kind; repeat updates note/times). Exact ISO times require explicit timezone, both values, end>start and duration<=36h. Start's UTC+05 local date must match date. note<=500. `DELETE /shifts/:id` owner only → `{ok:true}`.

Shift item: `{id,date,kind,startAt,endAt,note,author,createdAt}`. Without exact times, startAt/endAt are null and the entry is a calendar plan, never live presence. Shared calendar means saved shift declarations; it does not claim live GPS presence.

## Notifications and push

- `GET /notifications?before=<cursor>|after=<cursor>&unread=1&limit=50&type=chat|comment|sampling-round|work` → `{items,nextCursor}`, chronological paging as chat. Always scoped to caller. work includes comment and sampling-round before pagination; comment retains its exact previous meaning. Invalid types400; omit type for all types.
- `GET /notifications/unread-count` → `{count}`.
- `GET /notifications/:id` → `{item}`, recipient only, for native notification taps even outside the latest page.
- `POST /notifications/:id/read`, `POST /notifications/read-all?type=chat|comment|sampling-round|work` → `{ok:true}`; only recipient can mark read. work affects comment and sampling-round only, leaving chat unread. Omitted means all types; invalid type400. GET unread-count remains the global count for that recipient, independent of filter.
- `GET /push/public-key` → `{publicKey:string|null}`. Null means push not configured; persisted notification list still works.
- `POST /push/subscriptions` standard body `{endpoint,keys:{p256dh,auth},expirationTime?}` → `{ok:true}`. HTTPS endpoints restricted to browser push providers. At most ten per user; another account cannot overwrite an existing subscription.
- `DELETE /push/subscriptions` body `{endpoint}` → `{ok:true}`, owner scoped.
- `GET /devices/fcm/config` → `{enabled:boolean}`, authenticated. False means Android FCM server credentials are not configured; persisted notifications and Web Push still work.
- `POST /devices/fcm` body `{installationId,installationSecret,token,platform:'android',appVersion?,replaceOwner?:boolean}` → `{ok:true,deviceId,enabled}`. installationId is a per-install UUID; installationSecret is32 random bytes encoded as43 base64url characters, generated once and kept in Android encrypted private preferences. The server stores only their SHA-256 hashes. FCM registration token is an opaque20–4096 visible-ASCII string stored only in the private server table; never returned in API responses. appVersion is <=32 ASCII word/dot/plus/hyphen characters. At most ten devices per profile, enforced by unique slots in the database as well as validation.
- Registration retries and token rotation update the same installation. A different profile requires both matching installationSecret and explicit replaceOwner:true with the new profile's bearer. Wrong secret403; missing explicit switch409; token already associated with another installation409. The binding records the current session; a transactional session lock/recheck and captured owner/session/token-hash CAS prevent a stale authenticated registration from surviving logout or overwriting a concurrently renewed binding. An older same-profile login cannot take back a device already associated with a newer login:409 device_session_conflict. Equal creation timestamps of different logins also reject the takeover; a fresh login resolves this rare tie.
- `DELETE /devices/fcm` body `{installationId,installationSecret}` → `{ok:true}`. Only the current owner/session can remove its binding. Stale logout/unregister requests cannot remove a binding renewed in another session or profile. No list/read endpoint exposes device IDs, tokens or installation secrets.

Notification: `{id,cursor,actor:{id,nickname,avatarId,avatarMediaId}|null,type:'comment'|'chat'|'sampling-round',isMention:boolean,objectKey,objectLabel,noteId,parentId,preview,createdAt,readAt,periodKey,period}`. isMention derives from the persisted chat mentioned_user_ids and this recipient; old NULL means false. Mention push title is Вас упомянули · nickname; type remains chat. System sampling-round items have actor/noteId/parentId=null, objectKey=sampling, objectLabel=Отбор проб and their period metadata. Note and notification writes are atomic. Idempotent retries do not duplicate notifications or push. Root hook sendPush runs with ctx.waitUntil after persistence; provider failure never removes persisted notifications. VAPID private key stays server-only.

Ordinary new chat messages atomically create `type:'chat'` notifications for every other profile, excluding the sender. These use objectKey `chat`, objectLabel `Чат бригады`, and noteId/parentId equal to the message ID. Each recipient has a distinct opaque notification ID and receives corresponding delivery through independently invoked Web Push and Android FCM. Push recipients are processed two at a time after persistence. Exact clientId retries, edits and deletions create no new notifications. Chat deep links use GET /chat/messages/:id; deleted messages return404 and the UI can explain that the message was removed. The same authenticated, recipient-isolated notification feed serves Android fallback refresh.

Android FCM uses HTTP v1 with HIGH-priority DATA only `{notificationId,type}`. No author, title, message text or object name is sent through FCM. Native code fetches GET /notifications/:id using its currently encrypted bearer and chooses the channel from the authenticated response. Delivery selects only valid sessions and the persisted notification's recipient. UNREGISTERED responses remove only the exact captured device/user/session/token hash; rotated tokens survive delayed responses. Other provider failures preserve bindings and persisted notifications. Provider requests have10s deadlines, fixed Google destinations,32KiB response bounds and parallelism<=5. OAuth RS256 service-account assertions use the firebase.messaging scope, fixed OAuth audience and1h expiry; access tokens are reused with a60s safety margin and in-flight exchange deduplication.

FCM credentials are server-only: private app_secrets key `firebase_fcm` contains a standard service-account object `{project_id,client_email,private_key,private_key_id?}`; alternatively Edge secret FCM_SERVICE_ACCOUNT may contain this JSON. No credentials are committed in migrations, returned by config routes or sent to a client. Edge caches the private row for60s. The configured token_uri field is ignored; OAuth/FCM hosts are fixed. The native_push_tokens table has RLS enabled with no client grants, FK cascade from sessions/profiles, and no public policies.

Primary protocol references: [Google service-account OAuth](https://developers.google.com/identity/protocols/oauth2/service-account), [FCM HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api), [Android priority](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-priority), [FCM error codes](https://firebase.google.com/docs/cloud-messaging/error-codes).

Sampling scheduler: pg_cron runs a conditional check every minute in this existing project. A new circle or unfinished private ledger entry invokes POST /internal/sampling-round through pg_net; this route accepts no period/user inputs and never accepts an ordinary user bearer as authorization. Its separate random256-bit key remains in private app_secrets.sampling_scheduler.secret. The request carries X-Atlas-Scheduler-Time (epoch milliseconds) and X-Atlas-Scheduler (base64url HMAC-SHA256 of `POST\n/internal/sampling-round\n` + timestamp, with UTF-8 secret key). The database clock enforces age<=120s and future skew<=30s; signature comparison is constant-time. The managed net queue sees only this expiring proof, never the static key. Replaying a still-valid proof can only repeat the same idempotent current-circle check. See the [managed pg_net privilege limitation](https://supabase.com/kb/troubleshooting/revoking-access-to-pg_net-objects-has-no-effect).

The first scheduler invocation quietly records the current period without retrospective notifications. Later period starts atomically create the ledger and one deterministic notification/profile/period. Delivery uses a120s lease, persisted cursor and batches<=20 recipients. Durable retry_ids tracks only failed transient recipients: at most three attempts,60/120s backoff, same opaque notificationId. Providers mark only429/5xx/network as retryable; missing configuration/subscriptions and permanent4xx never cause endless retries. Other recipients continue without waiting for an individual's retry. Provider acceptance is best effort; persisted notifications always remain available. A crash may repeat an opaque delivery ID, which clients deduplicate. Scheduler activation is separate from schema migration and occurs after Edge publication; no open client is needed.

Schema changes live in db/schema.ts, generated SQLite QA migrations under qa/sqlite-migrations (production uses supabase/migrations). Request handlers never create tables or seed field data. `worker/registry.mjs` is generated from existing dist/data.json without changing source records.

Production migrations are `supabase/migrations/202611130001_brigade.sql` and `202611130002_api_rpc.sql`: private schema brigade, RLS enabled with no client policies and no anon/authenticated grants. Only service_role can execute `public.brigade_query_batch`. Adapter sends fixed server statements and JSON scalar parameters; PostgreSQL quote_literal binds each literal without scanning its contents as SQL, and each batch is one transaction. This RPC is never called with a user's SQL. Private Storage bucket: brigade-media. Root provisions it with public=false, file size<=2097152 and allowed MIME image/jpeg,image/png,image/webp. VAPID runtime row `brigade.app_secrets` key webpush_vapid has shape `{publicKey,privateJwk,subject}`; Edge caches for60s. This row is absent from migrations and all product endpoints. Root supplies it directly server-side.

Edge wrapper supplies requestIp to the API's rate limiter, preferring canonical CF-Connecting-IP and otherwise the last X-Forwarded-For hop; raw first-hop forwarding headers are not trusted. API module alone falls back to local when no platform IP exists. Hosted gateway behavior should be verified in deployment smoke tests; no IP is returned in product responses.
